    Customize: Add ADI Features to an Image

    A Kuiper image is basic or full only by which features were enabled when it was built: the “full” variant is the basic image with most of its CONFIG_* switches turned on. customize closes that gap after the fact — it takes a prebuilt basic image and installs the ADI features you pick (an XFCE desktop, the ADI libraries, the ADI applications) straight into it.

    The input may be a raw .img or a compressed/zipped one — the same set flash accepts (.img, .zip, .xz, .zst, .gz, .bz2). By default customize writes a fresh .img and leaves the input untouched; --in-place edits a raw .img directly instead.

    This works because every Kuiper image already carries the ADI apt repository, its signing key, and apt pinning. Each feature is therefore just an apt-get install run inside the image — the same path the Kuiper build itself uses. customize materializes a working image, loop-mounts it, runs those installs in its chroot, writes the few asset files apt cannot (systemd units, the desktop wallpaper, …), restamps the image identity, unmounts, and publishes the result.

    Note

    customize is Linux only and needs root. Because the Kuiper rootfs is ARM, customizing needs qemu-user-static (a.k.a. qemu-user-binfmt) and binfmt-support whenever the host cannot run the image’s binaries natively — an x86 host, or an arm64 host customizing a 32-bit armhf image. Only a host whose execution state matches the image (arm64 host ↔ arm64 image, 32-bit ARM host ↔ armhf image) needs no emulation. The .deb recommends these.

    list-features

    kli customize --list-features

    Lists the installable features — their ID (what you pass to --feature), GROUP (Desktop / Libraries / Applications), name, and a rough installed-size estimate. Needs neither root nor an image.

    customize

    sudo kli customize --image <file> [--output <file> | --in-place] \
                   [--feature <id> ...] [--all] \
                   [--grow <size> | --no-grow] [--arch armhf|arm64] \
                   [--overwrite] [--dry-run] [--yes]

    Install two features into a fresh image, letting the rootfs auto-grow to fit:

    sudo kli customize --image kuiper_basic.img \
    --feature libiio --feature iio-oscilloscope

    Build the “full” preset (every feature) straight from a downloaded .zip:

    sudo kli customize --image kuiper_basic.zip --output full.img --all --grow 6G -y

    Key behaviors:

    • Fresh output by default. customize writes a new .img and leaves the input untouched. Without --output the path is derived from the input next to it (kuiper_basic.zip → kuiper_basic-custom.img). --overwrite allows replacing an existing output file. --in-place instead edits a raw .img where it sits (no copy, no decompression — raw .img only).

    • Confirmation. Unless --yes is given, customize prints what it will do (and where it will write) and waits for y.

    • Auto-grow. The full ADI stack is multiple GB, so the rootfs is enlarged before installing. By default the grow is sized from your selection; --grow <size> sets it explicitly and --no-grow disables it. The rootfs must be the physically last partition (greatest end offset, not highest number — Kuiper’s small bootloader partition is numbered last but placed first).

    • Dry run. --dry-run prints the full plan — the resolved output path, the packages, files, and chroot steps per feature — without touching anything, as root or not.

    • No state tracking. customize installs what you select; apt is idempotent and resolves inter-package dependencies itself.

    On success it reports the output path, the features installed, the detected architecture, and the final image size, then hints at the matching flash command.

    Note

    The GUI exposes the same feature on Linux: select a local image and click Customize… on the Image card. The dialog lists the catalog grouped by Desktop / Libraries / Applications with size estimates, lets you auto-grow (or set an explicit size), pick the destination (or Edit in place for a raw .img), and runs the install in the elevated helper with live per-feature progress — the same core ImageCustomizer the CLI drives. On success the console switches to the freshly written image.

    The Desktop Feature

    The desktop feature reproduces the Kuiper build’s three desktop sub-stages: the XFCE4 environment and display manager; a headless X server and VNC (xserver.service + adi-xserver.sh on the dummy video driver, plus x11vnc.service), so the desktop is reachable on a headless eval board; and the cosmetic layer (dark theme, ADI wallpaper, menu names). The asset files it writes (service units, the 99-vc4.conf for RPi5 on arm64, the wallpaper and menu icon) are vendored verbatim from the Kuiper repo and embedded in the imager, so they stay byte-identical to the build. After a desktop customize the board auto- logs in as analog and exposes VNC (user analog, password analog).

    Architecture detection and the chroot

    customize reads the image’s architecture from its /etc/kuiper-release marker to pick the right emulator (arm64 → qemu-aarch64, armhf → qemu-arm). For an image without that marker, pass --arch. Emulation kicks in whenever the host’s execution state does not match the image’s — an x86 host, or an arm64 host with a 32-bit armhf image, since arm64 and armhf are distinct states and such kernels do not run 32-bit binaries by default. Then the kernel’s binfmt_misc entry for the target must be registered and enabled; when it carries the F (fix_binary) flag — the default with qemu-user-binfmt + binfmt-support — the kernel already holds the interpreter open and no copy into the chroot is needed. customize checks this up front and fails with a clear hint before it changes anything.

    After the installs, customize restamps the image identity so the result reports itself honestly: KUIPER_VARIANT becomes custom in both /etc/kuiper-release and the BOOT partition’s kuiper-release.json, and /etc/kuiper-packages is refreshed. Everything added only to run the chroot (a working resolv.conf, any staged emulator) is removed again, and the loop device and mounts are torn down on every exit path — success, failure, or Ctrl-C.
