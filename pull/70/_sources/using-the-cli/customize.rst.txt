.. _customize:

Customize: Add ADI Features to an Image
=======================================

.. description::

   Add the ADI "full-image" features (desktop, libraries, applications) to a
   prebuilt basic Kuiper .img, in place

A Kuiper image is **basic** or **full** only by which features were enabled when
it was built: the "full" variant is the basic image with most of its ``CONFIG_*``
switches turned on. ``customize`` closes that gap after the fact — it takes a
prebuilt basic ``.img`` and installs the ADI features you pick (an XFCE desktop,
the ADI libraries, the ADI applications) straight into it.

This works because **every** Kuiper image already carries the ADI apt repository,
its signing key, and apt pinning. Each feature is therefore just an ``apt-get
install`` run inside the image — the same path the Kuiper build itself uses.
``customize`` loop-mounts the image, runs those installs in the image's chroot,
writes the few asset files apt cannot (systemd units, the desktop wallpaper, …),
restamps the image identity, and unmounts.

.. note::

   ``customize`` is **Linux only** and modifies the ``.img`` **in place**. It
   needs root. Because the Kuiper rootfs is ARM, customizing on an x86 host also
   needs ``qemu-user-static`` (a.k.a. ``qemu-user-binfmt``) and
   ``binfmt-support``; on a native-ARM host no emulation is needed. The ``.deb``
   recommends these.

----

list-features
-------------

.. code-block:: bash

   kli customize --list-features

Lists the installable features — their ``ID`` (what you pass to ``--feature``),
``GROUP`` (Desktop / Libraries / Applications), name, and a rough installed-size
estimate. Needs neither root nor an image.

----

customize
---------

.. code-block:: bash

   sudo kli customize --image <file> [--feature <id> ...] [--all] \
                      [--grow <size> | --no-grow] [--arch armhf|arm64] \
                      [--dry-run] [--yes]

Install two features, letting the rootfs auto-grow to fit:

.. code-block:: bash

   sudo kli customize --image kuiper_basic.img \
       --feature libiio --feature iio-oscilloscope

Build the "full" preset (every feature):

.. code-block:: bash

   sudo kli customize --image kuiper_basic.img --all --grow 6G -y

Key behaviors:

- **In-place, with confirmation.** The image is modified where it sits. Unless
  ``--yes`` is given, ``customize`` prints what it will do and waits for ``y``.
- **Auto-grow.** The full ADI stack is multiple GB, so the rootfs is enlarged
  before installing. By default the grow is sized from your selection; ``--grow
  <size>`` sets it explicitly and ``--no-grow`` disables it. The rootfs must be
  the **physically last** partition (greatest end offset, not highest number —
  Kuiper's small bootloader partition is numbered last but placed first).
- **Dry run.** ``--dry-run`` prints the full plan — the packages, files, and
  chroot steps per feature — without touching the image, as root or not.
- **No state tracking.** ``customize`` installs what you select; apt is idempotent
  and resolves inter-package dependencies itself.

On success it reports the features installed, the detected architecture, and the
final image size, then hints at the matching :ref:`flash <flash>` command.

----

The Desktop Feature
-------------------

The ``desktop`` feature reproduces the Kuiper build's three desktop sub-stages:
the XFCE4 environment and display manager; a **headless X server and VNC**
(``xserver.service`` + ``adi-xserver.sh`` on the dummy video driver, plus
``x11vnc.service``), so the desktop is reachable on a headless eval board; and the
cosmetic layer (dark theme, ADI wallpaper, menu names). The asset files it writes
(service units, the ``99-vc4.conf`` for RPi5 on arm64, the wallpaper and menu
icon) are vendored verbatim from the Kuiper repo and embedded in the imager, so
they stay byte-identical to the build. After a desktop customize the board auto-
logs in as ``analog`` and exposes VNC (user ``analog``, password ``analog``).

----

Architecture detection and the chroot
--------------------------------------

``customize`` reads the image's architecture from its ``/etc/kuiper-release``
marker to pick the right emulator (``arm64`` → ``qemu-aarch64``, ``armhf`` →
``qemu-arm``). For an image without that marker, pass ``--arch``. On an x86 host
the kernel's ``binfmt_misc`` entry for the target must be registered and enabled;
when it carries the ``F`` (fix_binary) flag — the default with
``qemu-user-binfmt`` + ``binfmt-support`` — the kernel already holds the
interpreter open and no copy into the chroot is needed. ``customize`` checks this
up front and fails with a clear hint before it changes anything.

After the installs, ``customize`` restamps the image identity so the result
reports itself honestly: ``KUIPER_VARIANT`` becomes ``custom`` in both
``/etc/kuiper-release`` and the BOOT partition's ``kuiper-release.json``, and
``/etc/kuiper-packages`` is refreshed. Everything added only to run the chroot (a
working ``resolv.conf``, any staged emulator) is removed again, and the loop
device and mounts are torn down on every exit path — success, failure, or Ctrl-C.
