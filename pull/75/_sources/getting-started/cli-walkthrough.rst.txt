.. _cli-overview:

CLI Walkthrough
===============

.. description::

   The ``kli`` command line end to end: the conventions every command shares,
   then fetch, flash, configure, and customize

``kli`` is the command-line front-end and the scriptability surface of Kuiper
Imager. It is a thin layer over :ref:`libkuiper <core-library>`: it parses
arguments, renders progress, and translates typed results into output and exit
codes. The GUI and the CLI drive the *same* core, so they behave identically —
the CLI simply exposes it for scripting, automation, and headless machines.

.. code-block:: text

   kli version
   kli list-drives
   kli list-releases [--unstable] [--branch <branch>] [--limit <n>]
   kli list-projects --drive <dev>
   kli fetch     --image <id>   --output <path> [--force]
   kli flash     --image <file> --drive <dev>   [--yes] [--force] [--no-verify] [--timings]
   kli configure --drive <dev>  --project <name> --board <carrier> [--dry-run] [--force]
   kli customize --image <file> [--feature <id> ...] [--all] [--list-features] ...
   kli help

The guided order is **fetch → flash → configure**, and each command ends with a
``Next:`` hint toward the following one, but the steps are independent: flash an
image you already have, or reconfigure a card without reflashing.

----

Conventions
-----------

The Whole-Drive Model
~~~~~~~~~~~~~~~~~~~~~~

Every command that touches a card takes one identifier, ``--drive``, and it is
**always a whole drive** — ``/dev/sda``, ``/dev/mmcblk0`` (or
``\\.\PhysicalDrive1`` on Windows). You never name a partition. Kuiper Imager
enumerates the drive and identifies its BOOT, rootfs, and bootloader partitions
itself, by inspection (see the :ref:`layout rules <core-library>`). As a
convenience a partition node such as ``/dev/sda1`` is accepted and resolves to
its parent drive.

Output
~~~~~~

``kli`` produces **human-readable output only** — there is no JSON mode, because
nothing in the current design consumes one (see :ref:`architecture`). Output is
split by stream so it composes cleanly:

- **stdout** — results: drive tables, release listings, the final summary.
- **stderr** — everything else: progress bars, the flash confirmation prompt,
  and errors.

Progress is redrawn in place on stderr, so piping stdout to a file leaves you
with just the results.

.. _exit-codes:

Exit Codes
~~~~~~~~~~

``kli`` maps each error's :ref:`ErrorCode <core-library>` to a stable process
exit code, so scripts can branch on the *kind* of failure.

.. list-table::
   :header-rows: 1
   :widths: 10 26 64

   * - Code
     - Meaning
     - Typical cause
   * - 0
     - Success
     - The command completed.
   * - 1
     - Generic failure
     - Any error without a specific code (also: no arguments, unknown command).
   * - 2
     - Usage error
     - A missing or unexpected argument.
   * - 3
     - ``UserCancelled``
     - Ctrl-C, or declining the flash confirmation prompt.
   * - 4
     - ``PermissionDenied``
     - Raw device access without root; a rejected download token.
   * - 5
     - ``DeviceBusy``
     - A live mount / swap / LVM / RAID / LUKS holder on the target.
   * - 6
     - ``DeviceRemoved``
     - The card was pulled, or an I/O error during the operation.
   * - 7
     - ``InvalidImage``
     - The image or target isn't a usable file / block device.
   * - 8
     - ``DiskFull``
     - The image is larger than the target, or the download exceeds free space.
   * - 9
     - ``HashMismatch``
     - Read-back verification failed — the media doesn't match the image.
   * - 10
     - ``NotFound``
     - Drive, project, release, or artifact not found.

See :ref:`troubleshooting` for what to do about each.

Privileges and Tokens
~~~~~~~~~~~~~~~~~~~~~~

**Root.** Flashing and the Intel preloader write require raw device access, so
``flash`` and (for Intel projects) ``configure`` must run under ``sudo`` on
Linux, or from an elevated prompt on Windows. Without it you get
``PermissionDenied`` (exit 4) with a "run with sudo" hint.

**GitHub token.** Downloading a CI artifact with ``fetch`` needs a GitHub token
with the ``actions:read`` scope, discovered in order from ``$GH_TOKEN``, then
``$GITHUB_TOKEN``, then ``gh auth token`` (if the GitHub CLI is logged in).
Listing releases needs **no** token — a token there only raises the API rate
limit.

Inspecting drives and releases
------------------------------

``kli list-drives`` enumerates the drives you can write to, with columns
``DRIVE``, ``DESCRIPTION``, ``SIZE(GB)``, ``REMOVABLE``, and ``SYSTEM``. A disk
tagged ``SYSTEM`` hosts the running OS and is never a flash candidate.

.. _list-releases:

``kli list-releases`` lists available images as a table. The channel selects the
source:

.. code-block:: bash

   kli list-releases                     # stable: published Kuiper releases
   kli list-releases --unstable          # CI builds from GitHub Actions

- Without ``--unstable`` the **stable** channel is queried — published Kuiper
  releases from a hosted manifest, listed recommended-first (no token needed).
- ``--unstable`` lists **Kuiper 2.0 CI builds**. ``--branch <name>`` filters to
  one branch and ``--limit <n>`` sets how many recent successful runs to scan
  (default 10, max 100); both apply only to ``--unstable``.

The **IDENTIFIER** column (for example ``gh:9607528144`` for a CI build, or
``adi:2026.1.1/full/arm64`` for a stable release) is the copy-paste key you pass
to ``fetch``. See :ref:`releases-and-sources` for where each channel's images
come from.

.. _fetch:

fetch — download an image
-------------------------

.. code-block:: bash

   kli fetch --image <id> --output <path> [--force]

Downloads the artifact named by ``--image`` (an identifier from
``list-releases``) to ``--output``. The bytes are saved **verbatim** — no
decompression; the downloaded file is exactly what :ref:`flash <flash>` later
decompresses.

.. code-block:: bash

   kli list-releases --unstable
   kli fetch --image gh:9607528144 --output ./kuiper.zip

``--output`` may be a **file path** to write, or a **directory** (an existing
directory or a path ending in ``/``), in which case the artifact is saved under
its own canonical name. By default ``fetch`` refuses to overwrite an existing
file; ``--force`` allows it.

The download **streams to a sibling** ``.part`` **file and is renamed into place
only on success**, so a failed, cancelled, or interrupted fetch never leaves a
partial file at the destination. For a stable image whose manifest entry carries
a ``sha256``, the download is verified against it **before** the file is moved
into place, so a corrupt download never lands at the destination.

Downloading a **CI** artifact requires a :ref:`GitHub token <cli-overview>`; the
stable channel does not. CI artifacts are deleted by GitHub roughly 90 days
after their run — an expired one lists with ``STATUS`` ``expired`` and can't be
fetched; re-run ``list-releases --unstable`` for a current identifier. For the
full download mechanics, see :ref:`fetch <releases-and-sources>`.

.. _flash:

flash — write an image to a drive
---------------------------------

.. code-block:: bash

   sudo kli flash --image <file> --drive <dev> [--yes] [--force] [--no-verify] [--timings]

``flash`` writes a local image onto a card and verifies it. It is the one
destructive command, so it guards the operation with a confirmation prompt and a
suite of safety checks.

.. code-block:: bash

   kli list-drives
   sudo kli flash --image kuiper.img.xz --drive /dev/sda

``--image`` is a **local file** (download first with :ref:`fetch`). It may be a
raw ``.img`` or a compressed ``.zip`` / ``.xz`` / ``.zst`` / ``.gz`` / ``.bz2``,
decompressed inline as it is written. ``--drive`` is a whole drive. Flashing
needs root.

Before writing, ``flash`` prints a loud confirmation naming the drive it will
erase and waits for you to type ``y``; declining or Ctrl-C aborts (exit 3) and
touches nothing.

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - Option
     - Effect
   * - ``--yes`` / ``-y``
     - Skip the confirmation prompt. Use in scripts, once sure of the target.
   * - ``--force``
     - Bypass the *removable-drive* heuristic — for an internal SD reader or a
       ``/dev/loopN`` device. It does **not** bypass the system-disk guard.
   * - ``--no-verify``
     - Skip the full read-back verification (~half the wall-clock time). The
       partition table is *still* written last and checked, so a failed flash
       never looks bootable.
   * - ``--timings``
     - Print a per-phase wall-clock breakdown to stderr after a successful flash.

**Safety.** ``flash`` re-enumerates the drive up front and applies a two-tier
guard: the **system disk** (hosting the running OS) is refused **always** —
``--force`` does not override it — while a **non-removable disk** is refused
unless ``--force``. Read-back SHA-256 verification (on by default) proves what is
*on the card* matches the image, and the partition table is always written
**last**, so an interrupted flash yields an inert card, not a half-bootable one.
The full pipeline is in :ref:`flash-pipeline`.

.. _configure:

configure — set up boot files
-----------------------------

A freshly flashed Kuiper card is generic. ``configure`` specializes it for one
hardware combination — an eval board on a carrier — by copying the right kernel
and boot files into place. It is a C++ port of ADI's ``configure-setup.sh``.
**Raspberry Pi cards boot without this step and can skip it.**

First list the projects the card declares, then configure:

.. code-block:: bash

   kli list-projects --drive /dev/sda
   sudo kli configure --drive /dev/sda --project ad9081 --board vck190 [--dry-run] [--force]

``list-projects`` mounts the card's BOOT partition and lists its hardware
projects with columns ``EVAL BOARD``, ``CARRIER``, ``PLATFORM``, and ``ARCH``. A
project is identified by the **(eval board, carrier)** pair, which is exactly
what ``configure`` takes as ``--project`` and ``--board``.

Key behaviors:

- **All-or-nothing preflight.** Every source file (and, for Intel, the
  preloader) must exist before *anything* is copied, so a bad manifest never
  leaves a half-configured card.
- **Dry run.** ``--dry-run`` prints the exact copy plan without touching the
  card — the safe way to preview what a project will do.
- **Intel boards.** Intel-based projects additionally need a raw preloader write
  (which needs root) and an ``extlinux`` layout; both are handled automatically.
  Intel ``configure`` is Linux-only for now. See :ref:`configure
  <flash-pipeline>` and the :ref:`ConfigurationService <core-library>` for the
  mechanics.

.. _customize:

customize — add ADI features to an image (Linux only)
-----------------------------------------------------

A Kuiper image is *basic* or *full* only by which features were enabled when it
was built. ``customize`` closes that gap after the fact: it takes a prebuilt
basic ``.img`` and installs the ADI features you pick — an XFCE desktop, the ADI
libraries, the ADI applications — straight into it, **in place**.

.. note::

   ``customize`` is **Linux only** and modifies the ``.img`` **in place**. It
   needs root. Because the Kuiper rootfs is ARM, customizing on an x86 host also
   needs ``qemu-user-static`` and ``binfmt-support`` (the ``.deb`` recommends
   them); on a native-ARM host no emulation is needed.

List the installable features, then install:

.. code-block:: bash

   kli customize --list-features
   sudo kli customize --image kuiper_basic.img --feature libiio --feature iio-oscilloscope

.. code-block:: bash

   sudo kli customize --image <file> [--feature <id> ...] [--all] \
                      [--grow <size> | --no-grow] [--arch armhf|arm64] \
                      [--script <file>] [--dry-run] [--yes]

``--list-features`` prints each feature's ``ID`` (what you pass to
``--feature``), ``GROUP`` (Desktop / Libraries / Applications), name, and a
rough installed-size estimate. ``--all`` installs every feature (the "full"
preset).

Key behaviors:

- **In-place, with confirmation.** Unless ``--yes`` is given, ``customize``
  prints what it will do and waits for ``y``.
- **Auto-grow.** The full ADI stack is multiple GB, so the rootfs is enlarged
  before installing. ``--grow <size>`` sets the grow explicitly; ``--no-grow``
  disables it. (The rootfs must be the physically last partition.)
- **Dry run.** ``--dry-run`` prints the full plan — packages, files, and chroot
  steps per feature — without touching the image.
- **Architecture.** The image's architecture is read from its
  ``/etc/kuiper-release`` marker; pass ``--arch armhf|arm64`` for an image
  without that marker.

On success it reports the features installed, the detected architecture, and the
final image size, then hints at the matching :ref:`flash <flash>` command. For
the chroot/qemu model and the feature catalog, see :ref:`customize-pipeline`.
